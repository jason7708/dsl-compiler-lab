# Queue／window 的設計方向

記錄日期：2026-09-08。狀態：**已確認方向，尚未實作**。本文件記錄 DSL、共用 IR 與 backend 的責任，並保留尚待決定的語意；不是目前可用的 API 規格。

## 已確認的原則

1. DSL 描述 queue／window 的種類、保留範圍、需要的運算與精確度要求。範圍可以是筆數或時間，不限定為時間視窗。
2. IR 保留上述語意，不把固定陣列大小或 C++ 容器當成 window 的本質。
3. CPU backend 先允許可成長的精確時間視窗；第一階段生成使用 `std::deque` 的 C++23 實作可以接受，不要求先完成固定容量或硬體最佳化。
4. 未來部署到硬體時，由 target 選擇能實現相同語意的 queue／window，做資源配置與可行性檢查。無法滿足時明確拒絕，或由部署方選擇其他執行位置；不能默默截斷資料或降低精確度。

計算作者選擇資料結構的行為，backend 選擇實現方式。使用者也可以明確選擇有容量限制的種類，但不能要求所有時間視窗都額外指定一個最大筆數。

## 提供不同種類，而不是只有 time window

| 種類 | 計算上的意義 | 儲存空間與移除行為 |
| --- | --- | --- |
| FIFO queue | 依先進先出順序保存資料，由計算明確取出／移除 | 不隱含最近 N 筆或最近一秒；可提供可成長與有界種類 |
| 筆數 sliding window | 保存最近 N 筆資料 | N 是使用者要求的語意；加入第 N+1 筆時移除最舊資料，可用固定容量實作 |
| 時間 sliding window | 保存指定時間範圍內的資料 | 筆數隨事件密度改變，不能因底層容量不足就移除尚未過期的資料 |
| 明確允許近似的 window／摘要 | 在約定的時間解析度或誤差條件下提供統計 | 屬於可另行提供的種類；近似規格與 API 尚待設計 |

有界 queue 裝滿時要拒絕、等待或覆蓋，必須由該種類的契約明定。它和「最近 N 筆」window 的自動淘汰不同：後者移除第 N+1 舊的資料，本來就是所要求的計算行為。

種類的最終名稱、template 參數、建構方式與方法名稱尚未定案。預期以普通 C++ library 型別和方法呈現，不要求作者直接操作 backend 容器或學習硬體記憶體配置。

## 時間範圍與資源限制分開

「最近一秒」是計算需求；「最多配置多少記憶體」是部署限制。行情尖峰時，同一秒內的報價筆數可能大幅增加，因此不應在 DSL 自動加入一個任意的筆數上限。

可成長的 CPU 實作仍受實際記憶體限制；這不等於保證無限容量。資源耗盡必須有明確的錯誤或停止處理方式，不能悄悄改變結果。錯誤如何進入 unit／host 介面仍待設計。

對需要任意事件明細的精確視窗，不能同時承諾無上限的事件數量和固定記憶體。某些統計可以縮減儲存內容，但不表示所有 window 都能用固定大小的摘要精確實現。

例如平均值可以不保存完整 Quote，而保存需要的值、時間與統計量；然而任意時間邊界下，通常仍須知道哪些貢獻在何時過期。時間分桶可以減少資訊量，但部分邊界桶若沒有明細，可能改變精確視窗的結果，不能由 compiler 自動做這種替換。

## DSL、IR 與 backend 的分工

### DSL library

提供 queue、筆數 window、時間 window 等抽象，讓作者選擇並放在計算 struct 的成員中，使用新增、移除、推進時間、查詢及統計等操作。具體支援哪些操作需要另定規格，不預設所有種類都支援相同的方法。

同一個計算物件的多個 event 入口可以共用成員 window；不同 unit 的 window 各自獨立。成員與 local 物件的生命週期應延續既有 DSL 的物件所有權規則。

### 共用 IR

保留元素型別、保留策略、操作及可觀察的更新／錯誤語意。筆數 window 的 N 屬於語意；硬體配置的儲存深度則是 target 的資源資料。兩者可能相同，但概念上不可混用。

IR 不記錄 `std::deque`、allocator、C++ 方法名稱或硬體 queue 指令。新增何種型別／OP、如何表達狀態更新與驗證操作是否合法，應另行設計；本次不把它們宣稱為已存在。

### C++／CPU backend

第一階段允許以實體 runtime library 包装 `std::deque`，生成對應呼叫。目標是先實現清楚、可驗證的行為，再依測試與實際需求優化。筆數 window 也可以先用 deque，只要確實保留最近 N 筆。

這項選擇放寬了 CPU 第一階段「所有 state 都是固定大小且平坦」的要求。Deque 不是平坦可直接複製到硬體的資料布局；容器的配置與資源所有權屬於 CPU 實作，不能洩漏到共用 IR。

目前 compiler 只接受 scalar 成員與可展平的計算子物件，生成 state 也有 layout／copyability 檢查。因此不能只加入一個 deque header 就宣稱已支援；frontend 型別、IR、codegen、runtime unit 的 state／錯誤處理都需要配套。

### 硬體 backend

硬體未來可以提供固定深度 FIFO、ring buffer、時間淘汰 queue，或特定統計 window 等不同實作。部署時檢查容量、元素布局、時間解析度、吞吐量及最壞情況工作量是否符合要求。

「最近 N 筆」有天然容量上限；精確時間 window 若要使用固定容量，則需要額外的流量／資源契約，不能僅從「一秒」推導出安全的最大筆數。需要其他執行位置時，由部署方選擇，不隱含已有自動 CPU fallback。

## 時間 window 尚待決定的語意

以下是後續設計問題，沒有因本次記錄而視為已決定：

- 使用事件時間或處理時間；時間由 event／host 明確傳入的 API，以及整數時間戳的寬度、單位與溢位規則。
- 邊界是否採 `(t - duration, t]`，相同時間戳如何處理。
- 是否要求時間不倒退，或提供亂序、遲到資料的處理方式。
- 由新資料推進視窗，或另提供 `advance(time)`；沒有新資料時是否透過 TimerEvent 觸發查詢。
- 視窗尚未填滿與空視窗的統計結果，如何表達「目前沒有值」。
- Sum／mean 等運算的浮點契約；增量更新和每次重新加總可能有不同捨入結果，不能只用「精確 window」承諾位元完全一致。

精確視窗首先要求正確選取應保留的事件。統計的數值精度是另一份需要明確定義的契約。

## State 提交與錯誤

既有 unit 採成功才提交 state 的行為。加入 queue／window 後，仍須確保後續計算失敗時，不會留下部分新增或移除。

現有 runtime 要求 state 可無例外複製指派；直接使用 deque 不符合這項條件。實作時需要設計候選 state、提交與資源失敗的處理，不能只移除 static_assert 就視為完成。完整複製可以是待評估的正確性基線，但大量 window 每個 event 都複製可能很昂貴；日後可考慮只提交變更或其他 backend 策略，保持相同可觀察語意。

CPU 記憶體配置失敗如何傳到 host、如何與 DSL typed error 區分，以及能否保留生成碼的 `-fno-exceptions` 執行模式，都屬於第一階段需處理的問題，不在本次指定解法。

## 建議的實作與驗收順序

1. 定義各種類的最小 API、保留／移除規則、空值、錯誤與數值契約，再建立 IR 型別與操作驗證。
2. 可以先從筆數 window／FIFO 建立容器 state 與提交機制，再實作較複雜的時間 window；CPU 先用 deque 是可接受的起點，順序尚非實作承諾。
3. 以參考事件序列驗證：最近 N 筆、時間邊界與相同時間戳、尖峰大量事件不截斷、批次過期、多入口與不同 unit 隔離，以及新增／移除後失敗的回滾。
4. 依選定規格驗證亂序、空視窗、資源耗盡及浮點統計，再測量尖峰流量和多個 alpha 的記憶體／延遲。
5. 選定硬體 target 後，比對同一份語意的執行結果與資源能力；不支援的情形要明確拒絕。
